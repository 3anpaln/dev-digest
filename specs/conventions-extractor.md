# Conventions Extractor

Draft · M2 · 2026-11-27

## Problem and goals

Repository maintainers infer team conventions from recurring patterns in code. New contributors and review agents can miss those conventions when they are scattered across files. DevDigest should help maintainers find the patterns, verify them against the source, and turn the agreements they approve into reusable review guidance.

- Run a scan for the selected repository and identify which commit was analyzed.
- Give every finding verifiable code evidence and an independent review decision.
- Create one editable `repo-conventions` skill draft from the accepted findings and save it as version 1 in Skills Lab.

## User stories

- As a repository maintainer, I want to scan and re-scan my repository so I can discover team conventions in the code we use today.
- As a maintainer, I want to inspect code evidence, edit the wording, and accept or reject findings individually so I can decide which patterns reflect team agreements.
- As a maintainer, I want to edit the title, description, and Markdown of a skill based on my accepted findings so I can save the guidance I reviewed or discard the draft.

## P0 requirements

### Scan a repository

- Add **Conventions** under Skills Lab at `/repos/:repoId/conventions`. Use the existing repository selector and deep-link to the selected repository. The app shell already recognizes `/conventions` as an active route. Add the corresponding navigation entry and page. Reuse the headings, empty state, **Run extraction**, and **Re-scan** translations. Use the finding-level **Review decision** control and the page-level **Create skill** action for the accepted set. With no repository selected, direct the user to select or add one. [App shell](../client/src/components/app-shell/helpers.ts#L31) · [Navigation](../client/src/vendor/ui/nav.ts) · [English messages](../client/messages/en/conventions.json)
- Put **Branch**, **Folder**, **Source files to scan**, and **Max response tokens** in a **Scan options** disclosure that starts collapsed. A first run uses `main`, a blank folder, 20 files, and 5,000 response tokens per model batch. The primary action works with those defaults without opening the disclosure. Re-scan preloads the last settings for the selected branch and allows edits.
- When the selected branch has no scan attempts, follow the supplied first-run mockup. Show **Conventions in {owner}/{repository}** with a short description at the top. Center a checklist icon, **No conventions extracted yet**, explanatory copy, and a single **Run extraction** button in the page content. Keep collapsed **Scan options** available near the header. Show findings actions, counts, and scan history when applicable after an attempt exists. Keep first-run, active, failed, and successful zero-finding states distinct.
- Accept a branch name and validate it as a Git branch ref. Resolve it in the local clone when queuing the scan, then pin the resolved commit for file reads, model batches, and evidence links. The user supplies the branch name. If it is unavailable locally, identify the branch, offer the repository sync flow, and keep the chosen options for retry. Keep `main` as the initial choice even when the remote default is different.
- **Source files to scan** accepts a positive whole number as the distinct-file limit. Enter 0 to scan every eligible file in the selected scope in batches. Optional **Folder** limits eligible files to that repository-relative directory and its descendants. A blank folder makes the whole project eligible. With the default limit of 20, prioritize the most relevant files for convention extraction using likely entry points, related code, tracked layout, repository metadata, and import-graph signals when they correspond to the pinned commit.
- Show the requested limit, scanned branch and commit, completion time, files analyzed, skipped candidates, and whether a positive limit was reached. Exact copies count once toward the limit. Show **No conventions found in the scanned files** when a completed scan yields zero findings. A usable clone is sufficient to start the scan. Resolve the model through the workspace's Conventions feature settings and report scan failures.
- Look for reusable patterns such as naming, module structure, error handling, and persistence. Each proposed rule should say when it applies. Require corroborating examples across scanned code before generalizing a pattern, and retain the narrower scope when the repository uses different patterns in different areas. Publish one finding per distinct convention with examples grouped under it. For example, the Order, Ticket, and Refund decorators in the mockups can support one rule about TypeORM entity definitions.
- Write generated finding rules in English regardless of the language used in the scanned source. Preserve source identifiers, file paths, and code evidence verbatim.
- Surface up to five new or pending findings per attempt. Keep each rule to one actionable English sentence of up to 240 characters with an explicit scope and at least two verified examples. Prefer specific choices that affect how a change is written or reviewed. Omit general advice, incidental similarities, and duplicate rules. A repository-wide rule requires verified examples from different files and, when eligible files were left out, different directories. Show fewer findings when the evidence supports fewer rules.
- For each finding, show the rule, confidence estimate, and supporting evidence. Show the number of verified examples and distinct files alongside confidence, for example **3 examples across 2 files**. Count duplicate citations to the same span once. Evidence includes a repository-relative path, line range, and a short excerpt verified against the scanned commit. Build **View on GitHub** links from repository metadata and pin them to those lines at that commit. Show every finding returned by the latest successful scan, including rejected findings.
- Run extraction in the background. A second request for the same repository while a scan is active returns the existing scan. Reloading or switching repositories and returning shows the scan's current state. Keep the last successful results available while scanning and after a failed re-scan. Distinguish a successful scan with no grounded findings from a timeout, invalid model response, or repository read failure.
- Show the ten most recent scan attempts for the selected repository and branch under **Scan history**, newest first. Show when each attempt was queued, its status, branch name, configured provider and model, and the number of findings grounded in that scan. Link the branch name to GitHub in both scan history and the latest scan summary. Display the abbreviated scanned commit SHA as text. Carried-forward findings with earlier evidence do not contribute to the count. An unfinished or failed attempt displays **No result**. A completed scan can show **0 findings**. Older attempts without stored model details display **Model not recorded**.
- Show each attempt's folder or whole-project scope alongside its file limit, with the status and time prominent and branch, revision, scope, and model settings grouped into labeled details. Provide expandable file lists for the latest attempt and each history entry. Use **Analyzed files** for completed scans and **Selected files** for unfinished or failed scans. List eligible files skipped during selection with their reasons. Link each listed path to its file on GitHub at the scanned commit. Record each path once, even when a file spans several batches. Keep partial lists for failed attempts and distinguish older attempts with unavailable details.
- Offer **Max response tokens**, a positive whole number with a default of 5,000. Preselect the last recorded value on re-scan. Apply the configured maximum to each model response independently and record it in scan history for successful and failed attempts. If the provider reports that a response hit the limit, report that reason and let the user retry with a higher value. The token limit is separate from the file limit and the five-finding limit.

### Review findings

- Use the mockups' repository heading, accepted count, evidence cards, confidence indicators, and page-level **Create skill** action. The count is the number of accepted findings out of all findings in the current result set.
- Each finding starts **Pending**. A single **Review decision** control in the card header shows the saved status and lets users switch among **Pending** (amber), **Accepted** (green), and **Rejected** (red). Keep the status text visible. **Edit** opens the rule and scope editor. A saved edit preserves the finding's evidence, confidence estimate, and decision. Reject blank edits and keep unsaved text available after an error. Persist decisions and edits so they survive reload.
- Offer **Clear all decisions** when the selected branch has reviewed findings. Show a warning dialog with **Cancel** and **Clear decisions**. Cancel leaves review decisions intact. Confirmation returns accepted and rejected findings for that branch to Pending and clears their timestamps. Preserve rule text, scope, evidence, and saved skills. Clear historical review decisions for that branch so a later scan cannot restore them.
- Show an editable **Applies to** field on each finding. Prefill it with the scope inferred from the evidence, such as `src/billing/**`. Let users edit the scope independently of the rule text. Require an explicit scope and use **Entire repository** for a repository-wide convention. A scope edit preserves the evidence, confidence estimate, and decision. Persist it alongside the edited rule and retain the original inferred scope for re-scan matching.
- Group findings as **Pending**, **Accepted**, and **Rejected**, in that order. Start each group with a prominent, left-aligned heading and its finding count. Use a subtle divider and more vertical space between groups than between cards within a group. Align the cards directly under their heading and keep them together in a labeled section so the heading clearly applies to every card up to the next group.
- Let users expand and collapse each group independently using its heading. On entry, Pending starts expanded and Accepted and Rejected start collapsed. Keep the headings and counts visible in either state. Opening a reviewed group reveals the individual collapsed findings.
- Keep each finding's **Review decision** visible on its card. Show code evidence inline in the same group, directly inside the corresponding card. Pending cards show evidence immediately. Accepted and rejected cards start collapsed with the title, decision, scope, and confidence row. Expanding a card reveals its evidence, editing controls, and the date and time of the latest accept or reject decision within that group. Changing the decision records a new timestamp, editing text or scope preserves it, and returning to Pending clears it. Older decisions without a recorded time display **Decision time unavailable**.
- Keep findings and decisions separate by branch. On a successful re-scan, match findings from the same branch on normalized original rule and scope. Preserve saved wording, scope, decisions, and decision timestamps for unambiguous matches and refresh their evidence. New or ambiguous matches start pending. Keep previously accepted and rejected findings that were absent from the new scan with their prior evidence, pinned to the earlier commit. Reviewed findings sit outside the five-finding budget, remain in the group counts, and contribute to skill drafts for their branch when accepted. Apply the result atomically using the latest saved decisions.
- Summarize the latest successful re-scan, including how many decisions were kept, new findings appeared, and reviewed findings were kept with earlier evidence. Keep the summary available after reload.

### Create a skill

- Enable **Create skill** once at least one finding is accepted. Open the **Create skill from conventions** modal over the review list. Show its source repository and accepted count. The default name follows `<repo>-conventions`, such as `ai-customer-support-conventions`. Prefill a description and a Markdown body using the current saved wording of every accepted finding, including user edits. Use stable list order and keep each finding's scope in the generated text. Include editable **Name**, **Description**, and **Markdown body** fields. The Markdown field extends the name-and-description modal shown in the mockup.
- Build the draft from accepted findings on the selected branch. Include each finding's saved **Applies to** scope alongside its rule in the Markdown so module-specific guidance stays scoped. Pending and rejected findings contribute zero generated text. Raw evidence excerpts stay on the Conventions page. Track the source branch, commit, and finding IDs and revisions in server-owned provenance. Bind the draft to the originating workspace, repository, and branch. If the accepted set, saved wording, or saved scope changes before confirmation, show a conflict and let the user refresh the source while preserving access to their draft edits.
- **Cancel** discards the draft and returns to the review list. Ask before discarding edits through Cancel, Escape, or another close action. Opening, editing, and discarding the draft create zero library records.
- **Create skill** in the modal validates fields using the existing skill rules. The name and body are required. Save exactly the submitted Markdown with its whitespace and indentation intact. Create a skill of type `convention` and source `extracted` and its version 1 in one transaction. A retry of the same save returns the same skill. On success, close the modal and open the saved skill in Skills Lab. On failure, keep the modal and edits available for retry.
- Save the skill in the source workspace's library because the instructions can describe private code. Save it disabled and make it available for deliberate enablement and assignment through the existing Skills and Agent flows. The dialog identifies the workspace and initial disabled state. Later scans have no effect on the saved skill snapshot.

## Existing implementation and extensions

- **Findings storage.** Store findings in the existing `conventions` table. Its workspace and repository IDs scope the row. `rule`, `evidencePath`, `evidenceSnippet`, `confidence`, and `accepted` already cover rule text, a single code example, and basic acceptance. Extend this table through a new migration for scan linkage, original rule and scope, a three-state decision, and verified evidence ranges and additional examples. Map legacy `accepted` values of `true` and `false` to accepted and pending, respectively. Carry a legacy decision into a scan only when the original rule and scope match a newly grounded finding unambiguously. [Schema](../server/src/db/schema/knowledge.ts#L31) · [Existing migration](../server/src/db/migrations/0000_init.sql#L96)
- **API contract.** Extend `ConventionCandidate` in both vendored copies together. Its existing fields are `id`, `rule`, `evidence_path`, `evidence_snippet`, `confidence`, and `accepted`. The evidence path and snippet describe one code example. Add the explicit decision, saved scope, and evidence ranges and support multiple examples per finding. If the existing fields are retained for compatibility, derive the boolean from the decision and the singular evidence fields from the primary example. [Server contract](../server/src/vendor/shared/contracts/knowledge.ts#L175) · [Client contract](../client/src/vendor/shared/contracts/knowledge.ts#L175)
- **Scan lifecycle.** Reuse `JobRunner` and `jobs` for scan status, timestamps, and repository and commit metadata. Findings reference their scan so the latest successful result can be distinguished from a queued, running, or failed scan, including a successful scan with zero findings. Scope scan, read, edit, and skill creation operations to the authenticated workspace and repository. Guard publication so a timed-out or superseded attempt cannot replace the last successful results. [Job runner](../server/src/platform/jobs.ts) · [Jobs schema](../server/src/db/schema/ops.ts#L6)
- **File selection and grounding.** Enumerate regular tracked source from the pinned Git tree. For a bounded scan, prioritize one coherent area and prefer files that can corroborate provisional rules when filling the remaining budget. Exclude generated and vendored files, binaries, and known secret-bearing paths. First-party files under `lib/` and `packages/` remain eligible. Send only one copy of exactly identical content. Batch up to about 48,000 serialized characters. Count duplicate, oversized, blank, or unusable candidates as skipped. Keep absolute line numbers and merge verified evidence across batches. If any batch fails or the scan exceeds 10 minutes, keep the last successful results. Record the requested limit, analyzed and skipped counts, and budget result in scan history. [File selection](../server/src/modules/conventions/focus.ts) · [Extraction and grounding](../server/src/modules/conventions/extract.ts)
- **Model selection.** Resolve `conventions` through the existing workspace Feature Models setting, using the registry default when there is no override. For manual experiments, choose an inexpensive structured-output model supported by the configured provider in **Settings → Feature Models → Conventions**. Automated tests use fixtures. [Feature model registry](../server/src/vendor/shared/contracts/platform.ts#L74) · [Resolver](../server/src/modules/settings/feature-models.ts#L51)
- **Skill creation and ownership.** The existing `skills` table supports `type: convention` and `source: extracted`. Reuse skill-field validation and atomic skill/version persistence with an extractor-specific creation path that supplies the source workspace and server-owned provenance. The generic create path currently writes to the shared library and supports manual and import creation. Keep the existing Skills Lab list, detail, and version APIs for opening and managing the saved skill. [Skills schema](../server/src/db/schema/skills.ts) · [Skills routes](../server/src/modules/skills/routes.ts) · [Skills repository](../server/src/modules/skills/repository.ts#L60) · [Skills page](../client/src/app/skills/page.tsx)
- **Agent assignment and review.** Reuse the agent editor's Skills tab and `GET /agents/:id/skills` and `POST /agents/:id/skills` for ordered assignments. The review service resolves enabled assignments, and reviewer-core already renders their bodies under `## Skills / rules`. The extractor needs to register its server-verified creation provenance in the existing Studio skill classification so the reviewed body follows the same prompt path as other Studio skills. ## Success measures

- **Release gate.** All release acceptance scenarios pass, and every displayed fixture citation resolves to the scanned revision.
- **Pilot target.** At least 4 of 5 maintainers in a moderated pilot complete the scan-to-save journey without assistance. Record the number who successfully find evidence, make decisions, and edit and save a skill.
- **Follow-through target.** Within 30 days of the pilot, at least half of the repositories with a saved conventions skill use it in a Studio review of that repository. Measure from skill creation records and saved review skill snapshots. Treat both pilot targets as initial hypotheses.

## Delivery and follow-ups

The feature depends on a usable repository clone, Conventions feature-model settings, and the existing Skills Lab.

### Branch selection and scan options implementation plan

1. Add branch to the scan request, resolve the named local branch, and store the resolved commit and scan settings with the queued job. Link the branch in scan metadata and keep evidence links pinned to the scanned commit. Reuse branch names already stored on older scan jobs to keep their findings and history accessible.
2. Use authenticated workspace, repository, and branch scope for finding reads, re-scan matching, decision mutations, history, and skill drafts. Keep the existing one-active-scan-per-repository behavior.
3. Group the four fields into the collapsed **Scan options** disclosure and implement the first-run layout from the mockup. Verify starting with defaults, changing options, switching branches, and the first scan after syncing a previously unavailable branch.

- **P1 · Bulk triage.** Let users select multiple findings and apply one decision. Each finding remains independently reversible. This follows the individual review flow.
- **P2 · Refresh an existing skill.** Preview a diff from newly accepted conventions and save it as a new version after explicit review. The initial flow creates a new skill on each distinct confirmation.
- **P2 · Export and CI.** Consider downloading a `SKILL.md`, writing it into a repository, and using it in CI as separate delivery workflows. The current deliverable is a Studio skill.
